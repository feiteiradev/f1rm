# Keeping the human aligned during an autonomous run

Question: how do current agentic coding tools and spec-driven workflows keep the user's intent and the result the same during an autonomous run, without wasting tokens and time? And what fits f1rm, where the user sees only the final merge today?

Researched 2026-11-09 from primary sources (vendor docs, source repos, engineering blogs, papers). **Unverified** marks a claim I could not check at its source.

## Comparison

| Tool | Restates intent / asks first | Gates between phases | Acceptance format | Early slice | Action → requirement link | Live log | Mid-run steering |
|---|---|---|---|---|---|---|---|
| GitHub Spec Kit | `/clarify`: up to 5 questions, answers written into the spec | You run each command yourself, "reviewing each result before continuing" | Given/When/Then per user story | P1 story = MVP, "STOP and VALIDATE" | Each task tagged `[US1]` | none (it is templates) | edit the artifacts, re-run; `/converge` adds what is still missing as tasks |
| Kiro | generates requirements from the prompt for you to edit | Feature Spec: you review each phase; Quick Spec skips the gates | EARS `WHEN … THE SYSTEM SHALL …` | none | tasks "link each to requirements"; properties → requirement on hover | task status in-progress/completed | edit the spec files; tasks refresh |
| Claude Code | plan mode; spec interview pattern | approve plan (or "No, keep planning"; Ctrl+G edits it) | your spec / failing test | none | none | transcript | Esc, `/rewind`, `/clear` |
| Cursor | Plan Mode asks clarifying questions | click to build | none | none | none | none documented | edit the plan in chat or markdown |
| Windsurf (now Devin Desktop Cascade) | none documented | none | none | none | none | Todo list in the conversation | ask it to edit the Todo list; queued messages; named checkpoints and revert |
| Devin | Interactive Planning: files, findings, a draft plan before work | you change the plan before it runs | none | asks you to set checkpoints | none | Progress tab (shell, edits, browser) | chat, `/btw` side chats; Session Insights afterwards |

## The patterns

### 1. Restating intent / asking before work

- **Spec Kit** `/clarify` asks "up to 5 highly targeted clarification questions and encod[es] answers back into the spec", each answerable by multiple choice or "<=5 words" ([clarify.md](https://github.com/github/spec-kit/blob/main/templates/commands/clarify.md)). The spec template says "Mark all ambiguities: Use [NEEDS CLARIFICATION: specific question]" and "Don't guess" ([spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)).
- **Claude Code** suggests "Interview me until you could write the spec, then write it to SPEC.md", then building it in a fresh session ([best practices](https://code.claude.com/docs/en/best-practices)). **Cursor** Plan Mode: "Agent asks clarifying questions to understand your requirements" ([docs](https://cursor.com/docs/agent/planning)). **Codex**: "start with `/plan`", then let it interview you and write a goal with measurable success criteria ([long-running work](https://learn.chatgpt.com/docs/long-running-work)). **Devin** shows "relevant files, findings, and a preliminary plan" so "Devin's understanding of the task is aligned" ([Devin 2.0](https://cognition.com/blog/devin-2)).
- **Evidence.** ClarifyGPT (FSE 2024): asking clarifying questions raised GPT-4's pass@1 "from 70.96% to 80.80% on MBPP-sanitized" in a human evaluation ([arXiv 2310.10996](https://arxiv.org/abs/2310.10996)). A 2026 benchmark found current models still ask weak clarifying questions, and pass@1 on ambiguous requirements stays well below pass@1 on complete ones ([ClarifyCodeBench, arXiv 2607.00711](https://arxiv.org/pdf/2607.00711); I saw only the search summary, so **unverified**). Anthropic's field data: "On the most complex tasks, Claude Code stops to ask for clarification more than twice as often as humans interrupt it" ([Measuring agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)).

### 2. Approval gates between spec, plan and tasks

- **Kiro**: the only difference between Quick Spec and a Feature Spec "is whether you review each one before the next is generated". Kiro recommends gates when "Your team benefits from explicit approval checkpoints" or when you are "exploring unfamiliar territory", and Quick Spec for "a well-understood feature where you trust Kiro's output" ([best practices](https://kiro.dev/docs/specs/best-practices/)). Markdown Review lets you "comment on exact passages and send your comments to Kiro at once" ([specs](https://kiro.dev/docs/specs/)).
- **Claude Code** plan mode keeps edits blocked until you pick "Yes…" or "No, keep planning"; Ctrl+G opens the plan in your editor ([permission modes](https://code.claude.com/docs/en/permission-modes)). `/batch` "shows you the plan. Once you approve it, each unit gets its own worktree" ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Spec Kit** `/implement` treats unchecked checklist items as a "read-only gate … ask before proceeding" ([implement.md](https://github.com/github/spec-kit/blob/main/templates/commands/implement.md)). Its constitution requires "Tests are validated and approved by the user" before implementation ([spec-driven.md](https://github.com/github/spec-kit/blob/main/spec-driven.md)).
- **Where gates add friction.** Böckeler tried both tools: Kiro was "like using a sledgehammer to crack a nut", turning a small bug into four user stories. Spec Kit "created a LOT of markdown files for me to review … I'd rather review code than all these markdown files". She also "frequently saw the agent ultimately not follow all the instructions" despite the spec. Her evidence is anecdotal, with no measurement ([martinfowler.com](https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html)).
- **Evidence.** I found no study that measures phase gates against no gates. Anthropic's data cuts against gating every action: "effective oversight doesn't require approving every action but being in a position to intervene when it matters". Full auto-approve grows from about 20% to over 40% of sessions with experience, and interrupts grow from 5% to about 9% of turns ([Measuring agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)).

### 3. Acceptance criteria as concrete examples

- **Spec Kit**: each user story has "**Given** [initial state], **When** [action], **Then** [expected outcome]" and an "Independent Test" ([spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)). Its `/checklist` is "Unit Tests for English": it checks the requirements, not the code ([checklist.md](https://github.com/github/spec-kit/blob/main/templates/commands/checklist.md)).
- **Kiro**: EARS acceptance criteria ([feature specs](https://kiro.dev/docs/specs/feature-specs/)). "Kiro extracts properties from your EARS-formatted requirements" and turns them into property-based tests that keep "a clear, traceable link between your requirements and the tests" ([correctness](https://kiro.dev/docs/specs/correctness/)).
- **Claude Code**: "Does it know what done looks like? A goal condition, a spec file, or a failing test it has to turn green" ([best practices](https://code.claude.com/docs/en/best-practices)). **Codex**: "The goal text becomes both the first prompt and the completion criteria" ([long-running work](https://learn.chatgpt.com/docs/long-running-work)).
- **Evidence.** TiCoder has the user approve or reject generated tests before code is written. It gave "an average absolute gain of 45.97% in pass@1 … within 5 user interactions", and 15 programmers reported significantly less cognitive load ([arXiv 2404.10100](https://arxiv.org/abs/2404.10100)). Both TiCoder and ClarifyGPT measure single functions, not multi-ticket features.

### 4. Early previews, walking skeleton, first-slice demo

- **Spec Kit**: stories must be independently testable so that "if you implement just ONE of them, you should still have a viable MVP" ([spec-template.md](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)). The tasks template's "MVP First" strategy says: "**STOP and VALIDATE**: Test User Story 1 independently", and it has a checkpoint after each story ([tasks-template.md](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md)).
- **Anthropic long-running harness**: one agent writes a feature list where every entry starts failing. Each coding agent "work[s] on only one feature at a time" and edits only a `passes` field. Browser end-to-end checks caught bugs that unit tests and curl missed. One named failure is "Claude declares victory on the entire project too early" ([effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)).
- **Devin**: "Ask Devin to report back after completing each checkpoint or sub-task" ([instructing Devin](https://docs.devin.ai/essential-guidelines/instructing-devin-effectively.md)).
- **Evidence.** None measured for coding agents.

### 5. Live traceability

- **Kiro** "generates tasks and sub-tasks … and links each to requirements" ([introducing Kiro](https://kiro.dev/blog/introducing-kiro/)). Hovering a property shows "its connection to the original requirement and linked task" ([correctness](https://kiro.dev/docs/specs/correctness/)).
- **Spec Kit** task format `[ID] [P?] [Story]`, e.g. `T010 [P] [US1]` ([tasks-template.md](https://github.com/github/spec-kit/blob/main/templates/tasks-template.md)). `/analyze` is a "cross-artifact consistency and quality analysis across spec.md, plan.md, and tasks.md" ([analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)). `/converge` compares the code with the spec and "append[s] any remaining unbuilt work as new tasks" ([converge.md](https://github.com/github/spec-kit/blob/main/templates/commands/converge.md)).
- **Copilot coding agent**: each commit message links back to the session log ([track sessions](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/track-copilot-sessions)).
- **Evidence.** None measured.

### 6. Progress narration and human-readable logs

- **Devin** Progress tab: "All shell commands, code edits, and browser activity will be logged in one unified view". After the run, Session Insights shows an issue timeline and counts user messages: "A high message count can indicate that Devin needed frequent course corrections" ([session tools](https://docs.devin.ai/work-with-devin/devin-session-tools.md), [session insights](https://docs.devin.ai/product-guides/session-insights.md)).
- **Cascade** keeps "a Todo list within the conversation to track progress", which a background planning agent "continuously refines" ([Cascade](https://docs.devin.ai/desktop/cascade.md)). **Copilot** session logs show progress, token usage and session length ([track sessions](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/track-copilot-sessions)), but "Logs do not replace your own review and testing" ([about coding agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent)). **Codex** shows a goal progress row and gives a status recap on request ([long-running work](https://learn.chatgpt.com/docs/long-running-work)).
- **Claude Code**: ask for *evidence*, "the command it ran and its output, or the screenshot … For a session you weren't watching, it's also the only evidence you have" ([best practices](https://code.claude.com/docs/en/best-practices)). Anthropic lists transparency, "explicitly showing the agent's planning steps", as a core principle ([Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)).
- **Codex citing terminal logs and test output** as evidence: **unverified** (openai.com returned 403).
- **Evidence.** None on whether logs improve alignment. A caution: in METR's RCT, 16 experienced developers were 19% slower with AI yet "still believed AI had sped them up by 20%" ([METR 2025](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Feeling informed is not the same as being aligned. METR's own late-2025 follow-up calls its new data "an unreliable signal" ([METR 2026](https://metr.org/blog/2026-02-24-uplift-update/)).

### 7. Mid-run course correction without restarting

- **Claude Code**: "Watch the first minute, press `Esc` the moment Claude drifts, and after two failed corrections run `/clear`". Unattended: "you find out the next morning that it spent the whole night building on the wrong assumption" ([best practices](https://code.claude.com/docs/en/best-practices)).
- **Copilot**: type in the session log and "Copilot applies your input after it finishes its current tool call"; each steering message costs credits ([track sessions](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/track-copilot-sessions)). `@copilot` on a PR starts a new session, acknowledged with 👀 ([existing PR](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/coding-agent/make-changes-to-an-existing-pr)).
- **Cascade**: queued messages and named checkpoints you can revert to ([Cascade](https://docs.devin.ai/desktop/cascade.md)). **Codex**: follow-ups "add context or adjust constraints"; you can pause or edit the goal ([long-running work](https://learn.chatgpt.com/docs/long-running-work)). **Kiro**: edit `requirements.md` or start a spec session ([best practices](https://kiro.dev/docs/specs/best-practices/)). **Aider**: `/undo` ([git](https://aider.chat/docs/git.html)).
- **Evidence.** Experienced Claude Code users interrupt more (5% → about 9% of turns) as they auto-approve more ([Measuring agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)). That is correlational: it does not show that steering improves outcomes.

### Where gates pay off and where they cost

- **They pay off** where the ask is ambiguous, or the ground is unfamiliar (Kiro's own guidance). They also pay off when the human checks examples or tests rather than prose: the only measured gains, TiCoder and ClarifyGPT, come from humans answering small questions or approving tests.
- **They cost** on small, well-understood work (Böckeler; Kiro's Quick Spec exists for this). They also cost when the review artifact is long markdown, and when they ask for approval per action instead of a position to intervene (Anthropic).
- **No published study** measures plan/task gates, walking-skeleton demos or traceability against a baseline for agentic coding. Everything beyond clarification and test approval is vendor design rationale or anecdote.

## What fits f1rm

Today the PM interviews the user and the spec goes on Issues. Tickets, implement and close then run without the user, and close checks each acceptance criterion only at the end. Ranked by expected drift caught per minute of the user's attention:

1. **The PM ends on concrete examples the user confirms.** Before publishing, the PM shows 3–5 Given/When/Then examples of what the user will see when it is done. The user corrects or accepts them, and they become the spec's acceptance criteria, which close already checks. This is the pattern with measured gains (TiCoder, ClarifyGPT) and it costs no token-heavy run. *Attention: about 1–2 minutes, inside the PM session the user is already in.*
2. **The first ticket is a walking skeleton, and its demo goes on the spec.** The tickets step orders the P1 example's thin end-to-end path first. When it merges onto `spec-<n>`, the step posts the command it ran and its output (or a screenshot) as a comment on the spec, then carries on. This catches "built the wrong thing" after one ticket, not after all of them (Spec Kit MVP-first, Anthropic harness). *Attention: one glance per spec, mid-run, optional.*
3. **Every ticket names the example it serves.** Add a `Serves:` line next to `Boundary:`/`Depends:`. At the end, close posts one table on the spec: each example, pass/fail, and the evidence. Tickets that serve no example stand out as scope drift. *Attention: none required; it is what the user reads at the end, and it is shorter than the diff.*
4. **A user comment on the spec steers the next step.** The step prompt already reads the owner's comments. Make it explicit that a new owner comment on the spec, made mid-run, is read by the next step started. That step either folds it in as a new ticket or opens a decision ticket if it changes scope, so nothing has to restart (Copilot `@copilot`, Codex follow-ups). *Attention: only when the user chooses to. Cost: the change waits for the next step to start.*
5. **A plan preview that runs unless the user objects, for large specs only.** After the tickets step, post the ticket list mapped to the examples on the spec, and start implement after a short delay unless the user comments. Skip this for small asks (Kiro's Quick Spec vs. Feature Spec split). Don't make it a blocking gate: the evidence favours being able to step in over approving every step, and f1rm's runs are meant to be unattended. *Attention: about 30 seconds per large spec. A blocking version would cost the user's availability, so it is not recommended.*

Not checked: how `to-spec` and `to-tickets` currently phrase acceptance criteria, and whether the office already restarts a step on a new spec comment. Read both before building items 1, 3 and 4.
